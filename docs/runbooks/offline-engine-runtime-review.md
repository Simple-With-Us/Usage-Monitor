# Offline Engine Runtime Review

This is an offline source-review artifact.  Its tests use synthetic files, connections and archives.  A subsequent separately released isolated synthetic archive rehearsal and exact cleanup are scoped in the [activation-controller evidence](kimi-zcode-activation-controller.md); those releases do not authorize this candidate against live resources.  The runtime/host/mounted execute CLIs and the real mutation route refuse unconditionally; the wire candidate has no default connection and rejects real HTTPConnection instances before connect.  The separately reviewed canonical Infisical controller retains its own finite credential-use gate and is not released by this artifact.

`offline-engine-runtime.py` adds a fixed-file snapshot reader and finite wire protocol.  The [Engine API archive endpoint](https://docs.docker.com/reference/api/engine/version/v1.53/) returns tar data for a container resource.  The reader permits only the confirmed fresh full replacement ID and `/run/secrets/telemetry-hub.json`, with exact inspect identity/name/image/config/state checks before and after each archive.  It reads once while stopped and once while healthy, shares the lifecycle's route/count policy and refuses retry, another path or another ID.

The [in-memory tar reader](https://docs.python.org/3/library/tarfile.html) never extracts a filesystem path.  It accepts one exact regular filename, UID/GID `10001`, mode `0600`, at most 1 MiB of UTF-8 snapshot data and the reviewed whole-snapshot hash.  Compression, traversal/alternate paths, links/devices/sparse entries, multiple members, missing end blocks, trailing data and unreviewed prefix/PAX fields are refused.  One bounded PAX timestamp record is supported.  Production daemon tar representation, custody and mount behavior remain unverified; the separate synthetic rehearsal used different file ownership and its complete inspect check failed.

The finite HTTP candidate records durable intent, pins one root socket/peer connection, verifies the daemon on that same connection and rechecks the exact serialized body before send.  Intent, connect, probe, request, response and private response durability share one 15-second deadline.  JSON bodies are capped at 1 MiB; total response headers/body/framing are capped at 2 MiB to allow the bounded tar wrapper.  Warnings/status responses are privately acknowledged before interpretation.  Unknown responses, count exhaustion, changed/closing connections and receipt failure are terminal without reconnect, retry or automatic rollback.

The shared logical request ceiling is now `30 + 2 * health_checks`, including the archive reader's six reads.  The wire ceiling is twice that minus the one reused initial info probe.  With three health samples, the ceilings are 36 logical and 71 wire requests; the complete healthy synthetic filesystem/HTTP flow uses 32 logical and 63 wire requests.  Transport/proof/sink resources close only after synchronous work returns.  These are tested offline counts, not production receipts.

## Archive-Extended Rehearsal Requirements

This addendum supersedes the configuration-only 29-request proposal in the earlier rehearsal plan.  Retain its exact proposed disposable A/B/journal/RAM names and production-resource exclusions.  After each stopped A/B inspect, add one GET of the exact synthetic snapshot archive and one post-read inspect while still stopped.  Validate the same synthetic bytes, custody and unchanged projected configuration.  The extended proposal has 27 explicit logical calls; probing the daemon on the same connection before every operation except the initial info read gives 53 wire requests and a proposed hard maximum of 54.  The final closed isolated executor must independently recompute and test those counts before any release.

A stopped-container archive GET can cause the daemon to mount filesystem views or invoke a volume driver.  Those effects require review; GET alone is not proof of zero host effects.  Production image/field-set metadata, host-network behavior, fixture label/path substitutions, UID/custody, exact daemon identity, tar representation and the new isolated executor/source/plan hashes remain prerequisites.  No production mount, snapshot, volume, producer token or service grant may be used in the rehearsal.  Any ambiguous result preserves owned resources for a separately reviewed bounded reconciliation/cleanup plan.

## Current Validation And Remaining Gaps

The full suite has 118 tests: 116 pass as the host user and two existing UID-assignment tests skip.  Five new regressions exercise full-field resolved mount-order normalization, source immutability, malformed/duplicate destination refusal, reordered replacement acceptance and duplicate refusal before stop/start.  Fifteen runtime tests exercise strict archives, disabled/default routes, daemon/connection identity, lost replies, exact route/order refusal, receipt deadlines, wire/header/framing caps, root peer, reader digest/state/parse deadlines and the complete shared-budget host flow.  Earlier review regressions also require final staged-file byte/identity/full-stat validation and exact physical stopped/prestart journal fingerprints.  Legitimate poststart file movement can accompany nondecreasing journal progress.

Independent integration review found no blocking issue within the offline reader/wire scope; the new mount-order predicate awaits its own independent review.  No production binary reader or mutation transport is wired, and current tests use fake connections and synthetic files/archives.  Cooperative compare/rename races and nonpreemptible kernel I/O remain limitations.  Production recovery/journal/custody evidence, production Engine archive acceptance, any further separately released isolated rehearsal and final sender/Sentry/Usage Monitor ACK/ledger acceptance remain separate gates.
