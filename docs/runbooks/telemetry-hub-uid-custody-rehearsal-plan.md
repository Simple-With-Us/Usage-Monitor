## Ownership Creation Without Starting A Process

The [Engine API 1.53 archive endpoint](https://docs.docker.com/reference/api/engine/version/v1.53/) supports uploading a tar to a container directory, including ownership and overwrite-control query parameters.  The proposed exact route is `PUT /v1.53/containers/{fresh-full-id}/archive?path=%2Frun%2Fsecrets&noOverwriteDirNonDir=true&copyUIDGID=true`, with a frozen uncompressed tar body and `Content-Type: application/x-tar`; require status 200 and retain the bounded response before interpretation.  No start, exec, stop, kill, network-create, volume-create, pull, build, prune or force route exists in this proposal.

Current upstream [Moby extraction code](https://github.com/moby/moby/blob/master/daemon/archive_unix.go) checks the destination's writable mount and applies container-user ownership options when requested.  Its [numeric user mapping implementation](https://github.com/moby/moby/blob/master/daemon/archive_tarcopyoptions_unix.go) maps the explicit container UID/GID to host ownership.  The handler has no running-state requirement; using it with a stopped fixture is an inference from that source and remains unverified on the installed daemon.  This is design evidence, not proof of the installed daemon version or its mapping.  Actual host lstat and returned tar ownership must both equal `10001:10001`; any other mapping or a read-only-root rejection stops without changing flags or retrying.  This route avoids assuming that tar header ownership alone proves real file custody.

The outgoing tar must be built and independently validated offline before any send: exactly one regular `telemetry-hub.json` member, no directory entries, path separators, traversal, prefix/PAX extensions, links, devices, sparse data or compression; numeric UID/GID 10001, mode 0600, deterministic metadata, exact bounded synthetic bytes and only zero end padding.  Freeze the complete tar length and SHA256, maximum 16 KiB, plus the snapshot SHA256.  Revalidate the exact body and registered full ID immediately before the single upload on the pinned connection.  `noOverwriteDirNonDir` alone does not prevent file overwrite; the empty pinned host directory, strict member allowlist, one-attempt upload and no competing writer are essential gates.
