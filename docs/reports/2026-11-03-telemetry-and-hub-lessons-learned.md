# Telemetry And Hub: Lessons Learned

**Review window:** October 30–November 3, 2026, through the 8:46 AM closeout.  This is a historical lessons-learned snapshot, not a current runtime inventory.  It summarizes implementation, bounded historical reconciliation, and verified outcomes; it does not establish present-day deployment or collection state.

## What happened

The work addressed SQLite ingest contention, duplicate historical telemetry, collector profile discovery, unmeasured calls, ambiguous OTLP acknowledgments, and verification of a telemetry hub upgrade.  The reported SQLite `Operation has timed out` wording did not establish its cause: a two-connection WAL regression reproduced the same adapter error from a snapshot write conflict, while the original production root cause remains unproven.  The ingest path now reserves the SQLite writer before replay checks and returns a bounded busy response for explicit busy/locked errors ([PR #1842](https://github.com/Simple-With-Us/Usage-Monitor/pull/1842)).

A reviewed historical cleanup removed 201,252 exact duplicates across 2,013 shards, with matching tombstones and no keeper failures or missing receipts.  It retained 4,317 candidates without sufficient keeper proof and 548 older rollup groups.  These are bounded results, not permission for additional deletion ([PR #1846](https://github.com/Simple-With-Us/Usage-Monitor/pull/1846)).  For the October 29–30 Claude catch-up, 49,976 components projected to 12,508 unmeasured-call logs; the bounded delivery stored all 12,508, with no measured spans.  A separate historical child catch-up verified all eight retained Usage Monitor events, including one completed usage call with input 9,414, output 2, and cache read 512 tokens.  One associated Sentry span was stored with those token values and an exact `duration_ms` tag of 1,960 ms; the backend’s built-in duration differed by 0.0002 ms, within an explicitly stated 0.001 ms tolerance.

## Lessons to carry forward

1. **Use an evidence ladder for telemetry claims.**  A configured endpoint or flag proves intent; a validated ACK supports receiver acceptance; an explicit persisted-count receipt reports insertion; and an independent stored-row read verifies storage.  HTTP success alone is insufficient, and an idempotent duplicate may add no new row.  Accounting or suppression requires its own proof, such as an authenticated billed-call identity and exact quantities.  The child Usage Monitor receipt alone did not establish first-class project attribution or Sentry storage; the latter needed a separate query.

2. **Preserve uncertain usage and deduplicate only on exact evidence.**  Earlier time-window and session overlap could not establish that a producer call was billed, so uncertain events remain additive.  Child suppression is opt-in and requires an authenticated, persisted single-call receipt matching session, call, model, host, and token components; missing or ambiguous proof keeps the event ([PR #1844](https://github.com/Simple-With-Us/Usage-Monitor/pull/1844), [PR #1847](https://github.com/Simple-With-Us/Usage-Monitor/pull/1847), [PR #1848](https://github.com/Simple-With-Us/Usage-Monitor/pull/1848)).  Exact cleanup likewise needs durable keeper evidence, tombstones, and independently verifiable receipts.

3. **Discover each source profile independently and freeze identities before reconciliation.**  The collector initially treated discovery too narrowly.  Explicit OpenCode profiles now preserve standalone usage, retain the primary source, and avoid advancing checkpoints for unavailable explicit sources.  Plan against the full profile extent and frozen event IDs; do not infer identity from session or time proximity ([PR #1869](https://github.com/Simple-With-Us/Usage-Monitor/pull/1869)).

4. **Missing duration is not zero duration.**  A known call with no measured latency is a metadata log; an explicitly measured zero remains a span.  This preserves meaning and avoids fabricated timing.  For cross-system comparisons, preserve exact IDs, tokens, and the source duration tag, and state any numeric tolerance explicitly; here the accepted tolerance was 0.001 ms ([PR #1870](https://github.com/Simple-With-Us/Usage-Monitor/pull/1870)).

5. **Preserve durable intent for partial or ambiguous OTLP success.**  HTTP 2xx alone did not establish full acceptance.  The sender now validates bounded ACKs and rejection counts, holds an ambiguous batch with its durable pre-send intent, and persists confirmed sent receipts before clearing intent.  Rejection counts do not identify which records failed.  Recovery requires receiver/local reconciliation and a fresh sender instance.  Older senders ignore the intent, so rollback must preserve it and keep delivery stopped until reconciliation.  Unresolved batches must not be automatically replayed; explicit retryable failures retain their bounded retry contract ([PR #1874](https://github.com/Simple-With-Us/Usage-Monitor/pull/1874)).  The validation weakness was not established as the cause of the historical catch-up's transient count discrepancy.

6. **Compare before mutation and verify the resulting state independently.**  A stale upgrade plan was rejected on journal drift before mutation.  The stop requested container preservation, but the old container was removed; a verifier expecting it to remain therefore failed.  Independent readback established the stopped service, removed container, preserved volume and unchanged configuration before proceeding, without another stop request.  The same service was repinned and started, then independently verified healthy.  A cooperative reservation and fresh comparison are not an atomic provider-side compare-and-swap.  Preserve failed-attempt evidence and inspect state before retrying any mutation.

7. **Separate configuration truth from runtime injection.**  Scoped canonical settings were created and independently read back before local activation; active behavior was then verified through the actual configuration path.  A source-of-truth setting alone did not prove that the runtime injector had adopted it.  Preserve the working injection path until a replacement is independently active and verified; do not conflate secrets/configuration storage with process environment or deployment state.

8. **Make system boundaries and limits explicit.**  Native collectors own source observation and event identity; the collector delivery journal owns durable intent and receipts; the hub owns transport and ACK handling; Usage Monitor owns accepted usage rows and accounting semantics; Sentry owns its stored observability records.  A clean bounded log sample found no current ingest failures or timeout messages, but it did not establish the original SQLite timeout cause.  Likewise, stored child events and Sentry spans are separate evidence.  Keep each claim with its owning system and verifier.
