# Concurrent Backup Retention Prune Race

The pre-migration SQLite backup script prunes old backups to a retention count, and the default retention is one because the free tier has little disk.  Two Usage Monitor containers that share one `/data` volume can run the script at the same time.  The prune deleted the oldest managed backup by modification time with no coordination, so a concurrent startup could delete the file that the other startup had just promoted out of its `.partial` and was about to verify.  The victim then failed with `ENOENT: no such file or directory, stat '<dir>/.pre-migration-backups/prod.db.pre-migration-<ts>-<pid>.backup.db'` and exited non-zero, which aborted that startup.  The same test file is byte-identical on `main` and on the heads of the open pull requests, so the fault is in the base and not in any one of them.  The visible symptom is a startup that aborts on a shared volume, which is exactly the deployment shape the script exists to protect.

The prune now runs against settled backups only.  Each run captures a single start timestamp and treats every managed backup written after that moment as belonging to a concurrent startup that may still be verifying it; such a backup is never deleted and never counts toward the retention limit.  A backup is settled when it was last written before the run started, or when it is the run's own just-created backup.  This process's own backup is never a deletion candidate.  The prune count and the retention invariant are both computed over the settled set, so another startup's in-flight backup cannot inflate the count and trip the invariant error.  Normal operation is unchanged: with retention one and one pre-existing backup, that backup is still pruned once the new one is verified, and exactly one backup remains on disk.

The managed-backup listing also tolerates a file that disappears between the directory read and the stat, which the same shared volume can cause.  A file that is already gone is skipped instead of failing the whole backup run.

Focused tests cover the pruning decision without relying on timing: a backup newer than the start timestamp is never pruned, the run's own backup is never pruned, an older settled backup is pruned when retention would otherwise be exceeded, the settled-only invariant holds while another startup's backup is in flight, and a normal single-process run leaves exactly one backup on disk.  A second end-to-end test writes a backup that a concurrent startup promotes while the run is still copying and asserts that the run succeeds and that the promoted file survives.  That test fails against the previous script and passes against this one.  The existing concurrent-startup and stale-partial cleanup suites still pass unchanged.

This is source-level work only.  No production deployment or runtime verification is claimed here.
