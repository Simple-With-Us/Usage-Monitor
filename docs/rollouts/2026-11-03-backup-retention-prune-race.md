# Concurrent Backup Retention Prune Race

The pre-migration SQLite backup script prunes old backups to a retention count, and the default retention is one because the free tier has little disk.  Two Usage Monitor containers that share one `/data` volume can run the script at the same time.  The prune deleted the oldest managed backup by modification time with no coordination, so a concurrent startup could delete the file that the other startup had just promoted out of its `.partial` and was about to verify.  The victim then failed with `ENOENT: no such file or directory, stat '<dir>/.pre-migration-backups/prod.db.pre-migration-<ts>-<pid>.backup.db'` and exited non-zero, which aborted that startup.  The same test file is byte-identical on `main` and on the heads of the open pull requests, so the fault is in the base and not in any one of them.  The visible symptom is a startup that aborts on a shared volume, which is exactly the deployment shape the script exists to protect.

The prune now runs against settled backups only.  Each run captures a single start timestamp and treats every managed backup promoted after that moment as belonging to a concurrent startup that may still be verifying it; such a backup is never deleted and never counts toward the retention limit.  This process's own backup is never a deletion candidate.  The prune count and the retention invariant are both computed over the settled set, so another startup's in-flight backup cannot inflate the count and trip the invariant error.  Normal operation is unchanged: with retention one and one pre-existing backup, that backup is still pruned once the new one is verified, and exactly one backup remains on disk.

Deciding that a backup was "promoted before this run started" needs a witness that a rename cannot hide.  A rename preserves the file's modification time, so a promoted file used to carry the time its content was written; a startup that wrote its content early, stalled, and promoted later then looked like the oldest backup, and the prune could delete the file that startup was about to verify.  The settled check therefore uses two independent witnesses and requires both to agree.  First, the promoting process stamps the promotion instant onto the file's mtime before the rename, so the mtime is the moment the backup became visible rather than the moment its bytes were written.  Second, the run records the set of managed backup paths in the directory listing it takes when it starts; a managed backup only receives its `.backup.db` name when it is promoted into place, so a name that is missing from that listing was promoted after the run began, no matter what its timestamps say.  The listing witness also protects a mixed-version deployment, where an older container writes a backup without the mtime stamp.

The verification step no longer aborts the startup when a peer pruned this run's own backup.  The run re-reads the directory and prefers its own promoted backup; if a concurrent startup already pruned it under the shared retention count, the newest surviving backup is used as the restore point instead, because that backup was integrity-checked before its own promotion and covers the same database.  The run fails closed only when no verified backup survives at all.

The managed-backup listing also tolerates a file that disappears between the directory read and the stat, which the same shared volume can cause.  A file that is already gone is skipped instead of failing the whole backup run.  The prune count reports only the deletions this run actually performed, so a delete that raced with a peer and was skipped is not counted as pruned and cannot diverge from the number of prune log lines.

Focused tests cover the pruning decision without relying on timing: a backup newer than the start timestamp is never pruned, a backup promoted after this run started is never pruned even when the run-start listing already contains it, a backup that appears after the run-start listing is never pruned even when its mtime is old, the run's own backup is never pruned, an older settled backup is pruned when retention would otherwise be exceeded, the settled-only invariant holds while another startup's backup is in flight, the prune count reflects successful deletions only, the restore point falls back to the newest surviving backup, the promotion stamp makes the promotion time visible on the promoted file, and a normal single-process run leaves exactly one backup on disk.  A second end-to-end test writes a backup that a concurrent startup promotes while the run is still copying and asserts that the run succeeds and that the promoted file survives.  That test fails against the previous script and passes against this one.  The existing concurrent-startup and stale-partial cleanup suites still pass unchanged.

The retention unit tests are wired into the `test:backup-concurrent-startup` npm script, which the CI workflow already runs, so they can no longer be silently skipped.

This is source-level work only.  No production deployment or runtime verification is claimed here.
